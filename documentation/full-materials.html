Единая платформа уведомлений по банковским продуктам

Автор: Гладышева Ксения Владимировна • Baseline: BL-1 / v1.0

1. Контекст и границы

AS IS: продуктовые сервисы формируют суточные отчёты и имеют собственные модули уведомлений; нет единого владельца delivery status, retry и истории.

Цель: один согласованный дайджест по готовым отчётам клиента ежедневно к 09:30 МСК.

Масштаб: до 250 000 корпоративных клиентов; до 2 000 000 ReportReady-событий/сутки.

Report key: clientId + productId + reportType + businessDate + reportVersion.

IN: ReportReady ingest, dedup/idempotency, versioned digest, history/status, retry/quarantine/reprocess, observability, audit, phased migration. OUT: e-mail/push, персональные расписания, новый IdP, хранение PDF внутри платформы.

4. Архитектура и ownership

Event-driven ingest. Product Service владеет PDF/report metadata. Notification Platform владеет readiness state, digest/history/idempotency keys. Product services не обращаются напрямую к внутренней DB платформы. PDF не копируется: хранится protected URL/metadata.

Trade-offs: event-driven вместо polling → eventual consistency компенсируется dedup/retry/quarantine/reconciliation; один versioned digest вместо второго late-уведомления; собственная state DB вместо доступа к DB продуктов; SHADOW→CANARY вместо big bang.

6. Сценарии обработки

Happy path: ReportReady → broker → validate/dedup → state commit → ACK → digest publish/update → client GET.

Duplicate: duplicate → idempotent no-op; второго business effect нет.

DB outage: commit fail → no ACK → retry 5s/30s/120s → quarantine/DLQ → operator reprocess.

Late report: обновляет тот же digestId, digestVersion++.

Producer missing: выявляется reconciliation; consumer retry не может восстановить непубликованное событие.
